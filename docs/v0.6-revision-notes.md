## 1 · Corrections (v0.5 text is wrong or incomplete as stated)

### 1.1 Recovery reads a frontier, not only a pending stack  «R-1 · BLOCKER»

**Raised.** A crash after the retried operation's Commit (step 4, during a compensable
recovery) but before Resume (step 5) reaches the store state `[Done(op), Done(op')]`
with an **empty pending stack** and no final result. §8.1's dispatch reads "the top of
the pending stack"; §7.4's derived sequence ends at `Pending(op), Done(op')`. Neither
covers this state, and the v1 implementation wedged in it permanently: the privileged
completion refused a Done entry, violating its own declared idempotency.

**Disposition for v0.6.** Three connected changes:

1. **Recovery's selection input is the journal frontier** — defined precisely (the
   design review caught the draft wording as ambiguous, D-3): the frontier is the
   entry of **greatest insertion order**. Step 4's Commit updates an entry in place
   and does *not* advance the frontier — so after R-1's chain the frontier is the
   Done *child* even though the parent's Done was written later, and recovery is
   correct there precisely because completion is idempotent (its resumed continuation
   re-performs `complete(parent)` and receives the stored result). §8.1's crash-point
   table gains its missing generality: *frontier Pending → dispatch on δ; frontier
   Done → resume the named continuation with the stored result; no entry → the
   program entry point (see 2.1).* I1 (bounded pending) is untouched; it bounds the
   pending stack, which is a *sub-structure* of the journal, not recovery's whole
   input.
2. **§7.4's derived sequence gains a fourth row:**
   `Done(op), Done(op') → resume op''s continuation, whose next act is complete(op);
   complete of a Done entry returns the stored result.`
3. **The machine's own completion primitive is an operation with a delivery class,
   and Theorem 1's induction must use it.** `complete(j)` is declared idempotent;
   v0.5 never states that the *privileged* operations of the recovery machinery are
   bound by §8.3's equations exactly as foreign ones are. v0.6 states it as a lemma
   obligation: *every machine-local operation satisfies its declared equation, and
   Theorem 1's "crashes during recovery" case is proved by induction on the frontier
   with that lemma.* This was the review's deepest catch: the counterexample was found
   and repaired entirely inside the design's own vocabulary — evidence for the design,
   but only after the text says what the implementation now does.

### 1.2 Persistence preserves continuation identity, not only count  «R-4»

**Raised.** v0.5 §5 treats affinity as a per-continuation property but §6/§7.3 specify
encoding as if the frame graph were a tree. A continuation reachable from two frames
(first-class `k` stored and referenced twice) encoded as two copies; after a cold
resume, two independently consumable continuations existed — affinity silently became
per-copy.

**Disposition.** §6 gains a clause: **Repr is defined over the frame *graph*;
encoding preserves sharing of continuation values, and decode yields one cell per
persisted identity.** Consequence stated plainly: the affinity theorem quantifies over
persisted identities, and any encoding that duplicates a continuation is unsound even
if each copy is one-shot. (Implementation: encode-side sharing table with
back-references; tested.)

### 1.3 Totality of encode is over reachable machine states  «R-5»

**Raised.** Rule 2 says encode is total for well-typed K. A *consumed* continuation
lexically captured in an environment at a later suspension is reachable (affine typing
bounds *use*, it does not erase the binding), and v1 refused to encode it — a
reachable suspension that could never persist.

**Disposition.** Rule 2's totality claim is restated as ranging over **reachable
machine configurations**, and §6 specifies the consumed case: a consumed continuation
persists as a **tombstone** — identity and consumed flag, no frames — whose only
future is the affinity error. Alternative noted for the calculus: environments pruned
to the free variables of the remaining computation make the case unreachable and
shrink stores; v0.6 may adopt pruning as an optimization but the tombstone clause is
what makes Rule 2 true without it.

### 1.4 The no-replay claim, said precisely  «F-003»

**Raised.** After a committed step 4, a crash before the next Intend re-runs the pure
segment that *follows* the resume. Read casually, §7.1's "no replay" seems to forbid
this; plan §3.3's stop condition 2 nearly does.

**Disposition.** §7.1 gains one sentence: *the no-replay property is that a
continuation is never re-derived by re-executing pure code — the continuation that
receives r is always read from σ; pure execution forward of a resumed Done is ordinary
execution, not replay.* (This is what §8.1's After-4 row already implies; it should
not have to be inferred.)

### 1.5 §13.1's example must obey its own type system  «plan §2, adopted»

`Approval.request` re-asked on resume is a different question to a human; v0.6 changes
the settle example to `request : Summary -> Decision @at_least_once(ReqId)` with a
request-id witness, as the plan proposed. The demonstration fixture already behaves
this way (dedup by request id, decision replayed).

## 2 · Sharpenings (v0.5 is right but under-specified; the implementation forced a choice)

### 2.1 The empty-journal row  «F-002»

§8.1's "Before 1 / no entry" row gets its degenerate reading: with an empty journal,
the last committed continuation **is the program entry point**. One sentence; the
recovery driver's `.none` arm is this sentence as code.

### 2.2 Rule 3's privileged capability has a scope  «F-001 + R-2»

v0.5 (via plan §8) predicted recovery is "an ordinary program plus one privileged
capability." Two findings refine that into text v0.6 must carry:

- **The class's exact boundary** (F-001): pure reads of σ (`frontier`, `load_kont`,
  `load_result`, `comp_arg`) plus atomic completion of an already-intended entry.
  Nothing else was needed; the watch condition never fired.
- **The privilege is scoped to the driver's own frames** (R-2): once the driver
  resumes a program continuation, the program must not inherit the capability — in v1
  this was a leak (user code resumed by recovery could read σ and re-materialise
  continuations). v0.6 states: *Cap[Local] is granted by the restart entry point to
  the driver and is not among the capabilities re-granted to resumed program
  continuations.* Under the unification (item 3.1) this stops being a special rule
  and becomes ordinary capability discipline — which is the correct final form.
- **Materialisation is affine** (R-3): loading a persisted continuation is itself
  one-shot per run; `load_kont` of the same identity twice is refused. This is the
  store-level face of §5's affinity and belongs beside it.

### 2.3 persist(K) includes the suspended operation's effect  «F-007»

§10.2's `persist(K) = <frames, {(sig(E), compat(E)) | E in handled(K)}>` must define
`handled(K)` to include **the effect of the operation pending at K** even when the
remaining frames no longer reference it: recovery re-invokes that operation, and the
merchant case applies to it first.

### 2.4 Verification is dependency-precise  «Phase 2 finding»

§10.1–10.2 gain a sentence the implementation proved both directions of: a sleeping
continuation is stranded by a change to *what it still references* and by nothing
else. (Pin-the-implementation was rejected in v0.5 for stranding too much; v0.6
records that per-dependency Merkle closure achieves the intended precision, with
SCC-grouped hashing for mutual recursion.)

### 2.5 Absence is an identity  «R-6»

Code identity (§10.1) covers names that had **no** definition at persist time: the
header records them with an absence sentinel, and a definition *appearing* under a
name the sleeping code references is drift, symmetric with one changing.

## 3 · The structural change

### 3.1 One mechanism, made true: suspending effects are handled effects  «F-004 + R-7»

v0.5 claims durability, tool invocation, and capability control derive from one
mechanism. In v1 they derive from two: prompt effects go through `handle … using κ`
(T-Handle enforced), while suspending effects are discharged by a host registry that
consults no capability at the site; in-language handlers for suspending effects are
statically rejected as a stopgap. Demonstration B's containment is therefore proved
for the prompt half only.

**Disposition: adopted, as the headline change of v0.6.** The full design is
`unification-design.md` (draft 2, after its own adversarial review closed two
blockers: the all-paths-resume condition on suspending clauses, and the machine-local
dispatch mask retained as `Cap[Local]`'s dynamic proxy). In one paragraph: a
suspending effect is discharged by an ordinary installed handler whose clauses are
strictly tail-resumptive **on every control path** and whose only non-pure step is a
**foreign invocation** (`Foreign[τ1, τ2]`, the §6.2 discipline applied to the outside
world); the five-step protocol is not a second mechanism but *what the machine does
to execute a suspending clause* — Intend at capture, the clause body as the crash
window, Commit at the clause's tail resume, the window having exactly two exits by
typing. Capability, policy, budget, revocation, and recovery re-granting then hold at
suspending sites by the same T-Handle premise that already governs prompt sites, and
Rule 3's privileged capability becomes an ordinary `Cap[Local]` grant with a stated
dynamic mask.

## 4 · New evidence to cite (no text obligations, but §14/§16 should update)

- **§14 status table.** "Serialisable continuations are feasible" moves from
  *conjecture* to *demonstrated for the interpreter's value domain* (cross-process
  cold resume under hard process death; the general claim stays open). Theorem 1
  gains "counterexample found in implementation and repaired (R-1); the derived-
  sequence lemma is now a stated proof obligation." Rule 2 totality: corrected per
  1.3.
- **§16, the intended author.** First data: six fresh-context model instances given
  only a one-page reference card produced 6/6 first-pass-compiling programs across
  orchestration tasks, including the deliberate E004 temptation (answered correctly
  with a return clause) and a continuation-typed helper. Ablation machinery verified
  inversely (each restriction fails alone and switches off alone). Stated caveats:
  n=6, single model family, tasks calibrated to the worked examples; the convergence
  study on adversarial tasks remains to be run. The falsification condition (thrash /
  one restriction dominating) was not triggered — the quiet argument that the
  intended author is a checked generator is, so far, quieter.
- **§13 demonstrations.** A2's matrix gains the R-1 row (crash after retry-commit
  during recovery) — "mandatory before recovery semantics may be called implemented"
  now includes the case that was one crash deeper than v0.5's table.

## 5 · Explicitly unchanged (challenged in review, refuted, worth recording)

- The machine-local class does not violate plan §3.2's runtime allowance: step-2
  invocation plus the store's atomic commit are exactly the two things the runtime is
  permitted to supply (review verdict on the "hidden recovery machinery" claim).
- The tail/boundary discipline is per-clause, not per-continuation-identity; the
  proposed counterexamples fall outside the paper's own type grammar.
- Dependency-precise drift detection accepting changes to unreferenced definitions is
  intended behavior (§10.2's own argument), now tested in both directions.
